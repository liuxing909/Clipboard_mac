# 异常与压力测试记录

日期：2026-11-08。版本：0.1.8 的首版发布前修复。环境：Apple Silicon、macOS 26.3.2，release 构建。

## 第二轮复查结果

本轮继续追查内存增长，并增加存储随机种子、无纯文字回退的损坏格式和任务排队边界。以下问题均有失败复现或有效诊断证据，修复已包含在当前源码和通用安装包中。

| 场景 | 复查发现 | 当前处理 |
| --- | --- | --- |
| 损坏 RTFD 的虚拟分配 | 捕获原生反序列化异常仍不够；五个短样例各触发约 11.6 GiB 的未释放虚拟分配。 | 移除生产代码中的原生 RTFD 反序列化；有界读取已验证的 v0 平铺普通文件结构，先核对长度、数量和元数据，未知结构回退或拒绝。 |
| 系统合成富文本表示 | 三轮格式专项诊断报告 72 处、4,608 字节泄漏，调用栈来自快照读取系统合成文字。AppKit 的 item.types 本身也含合成类型。 | 通过公开 Pasteboard Manager 确认来源表示；不读取系统转换结果，后台提取正文。来源明确提供的文字仍保留，元数据暂时不可读则交原轮询重试。 |
| 相同内容重新复制 | 图片文件修好了，尺寸等元数据仍旧；富文本大小等错误也未恢复。 | 根据新副本重建派生信息，保留 ID、创建时间及固定状态。 |
| 缩略图失败或旧像素 | 损坏图片重新复制后仍显示空白，已显示的旧图也可能不刷新。 | 清理该摘要的失败状态、缓存和旧请求，刷新可见展示；离屏不触发解码。 |
| PNG 方向信息 | PNG 与生成的 TIFF 显示方向不一致。 | 保留原 PNG，生成 TIFF 时应用方向信息。 |
| 删除与复制同时发生 | 删除旧记录会丢弃无关新复制；修复后又发现尚未入队的同内容可在删除后重新出现。 | 以复制版本保存删除排除集合，覆盖已入队、压力重试及尚未取快照的复制；之后主动重新复制仍可保存。 |
| 清空与排队或保存失败 | 清空前尚未取快照的内容会回流；清空保存失败也会提前取消待处理复制。 | 清空成功后才取消采集并推进基线；失败保留原历史及待处理任务。 |
| 等待最新复制时按回车 | 压力恢复或队列满时可能粘贴旧记录。 | 默认等待最新内容；用户明确选择旧记录仍可操作；完成、拒绝或失败后退出等待。 |

### 最终验证

- **38 项核心测试通过**，八个固定种子、共 **4,000 次混合存储操作**。
- 最终通用构建在同一进程中连续 **20 轮、340 组应用自检通过**，约 **171.5 秒**。
- 其中包含 **8,960 个格式变异与对照输入**、**360 个 RTFD 结构拒绝用例**、**320 个删除/采集调度序列**及 **160 个未入队、压力和清空失败边界序列**。这些数量不等于真实用户复制次数。
- 最终包的格式专项另跑三轮 `leaks --atExit`：正常退出，**0 处泄漏、0 字节**。这只代表该专项在本次诊断中未检出泄漏，不是所有功能或所有输入无泄漏的证明。
- Intel 与 Apple Silicon 构建、本地签名、元数据及 DMG 校验通过；最低系统声明分别为 10.15 和 11.0。

### 内存测量

最终完整 20 轮的轮末物理内存从 **16.55 MiB** 到 **16.69 MiB**，各轮为 **16.55–16.74 MiB**。包含大图合成用例的进程峰值约 **171.67 MiB**，不能拿轮末值当峰值或正常使用占用。

分配器在用量从 **13.26 MiB** 到 **17.44 MiB**，第二轮起为约 **17.07–17.44 MiB**；分配器保留量为 **56 MiB**，AppKit 窗口数每轮均为 1。这些指标与物理内存含义不同，不能用单个计数证明无泄漏。

修复前的十轮格式专项，分配器在用统计从约 **62.19 GB** 增至 **621.84 GB**，但物理内存仅从约 **6.20 MiB** 到 **8.23 MiB**：前者主要是未触及的虚拟分配，绝不是实际占用了数百 GB 物理内存。有界 RTFD 读取后的二十轮中间验证不再出现该异常，轮末物理内存约 **6.30–6.39 MiB**（首末值）；最终包还包含后续合成类型修复。

结果、每轮采样及安装包 SHA-256 见 [recheck-0.1.8.json](../Benchmarks/recheck-0.1.8.json)。不同阶段增加了用例，不能据总耗时比较日常复制速度。

### 复现本轮检查

```sh
bash scripts/package-dmg.sh
bash scripts/test.sh
dist/剪贴匣.app/Contents/MacOS/ClipboardDeck --stress-test 20
MallocStackLogging=1 /usr/bin/leaks --noContent --atExit -- \
  dist/剪贴匣.app/Contents/MacOS/ClipboardDeck --stress-test 3 format-fuzz
```

诊断使用合成内容、命名剪贴板及临时历史，没有读取个人剪贴板或文档。源码包含可复用的回归用例；构建日志和临时诊断数据在被忽略的 `.build/`，不进入 Git 提交。

仍待真实 Word / WPS / Pages 窗口、跨应用快捷键和焦点切换、macOS 10.15 实机验证。当前安装包为 ad-hoc 签名，尚未公证。

## 第一轮记录（保留用于追溯）

以下是第一轮当时的结果；RTFD 的原生异常捕获方案已被第二轮有界读取替代，内存结论以本页第二轮记录为准。

### 已复现并修复

| 场景 | 修复前的实际结果 | 修复后的行为 |
| --- | --- | --- |
| 截断 RTFD | 33 字节样例触发 `NSDeserializeException`，进程 SIGABRT。 | 在小型 Objective-C 边界处理原生异常，回退有效纯文字；粘贴准备失败时保留目标内容。 |
| 截断 PNG | 141 字节样例可采集、入库，但 `prepareWrite` 报 `invalidImage`，记录无法粘贴。 | 采集和回写共用 PNG 块边界及结束标记检查，避免存入这类不完整原数据。 |
| 采集遇内存压力取消 | 未保存内容的复制版本被提前消耗，压力解除后仍不再采集。 | 重试最新内容；主动清空、暂停、停止会撤销重试，避免旧记录重新出现。 |
| 极端复制计数及损坏索引 | `copyCount = Int.max` 时再次复制导致 SIGTRAP；18 个损坏元数据场景没有被拒绝。 | 计数饱和累加；验证字节数、文字摘要、正计数和唯一 ID / 内容摘要，损坏文件保留原样。 |
| 损坏图片重新复制 | 再次复制相同图片返回成功，但已有坏文件未修复。 | 分块检查和原子修复图片，保留固定状态、条目 ID 和创建时间。 |
| 图片目录变成符号链接 | 新图片被写入链接指向的临时“外部”目录。 | 初始化和写入拒绝异常目录；清理也检查目录。本次未复现旧版清理误删。 |

另外补强单帧图片规则和索引大小边界：两页 TIFF 被明确拒绝，有有效文字时回退；超出默认 640 MiB 序列化预算的稀疏索引在读取前拒绝，小额度测试验证写入失败不覆盖历史。未实际制造内存耗尽或磁盘写满。

### 验证规模

核心测试 **35 项通过**，包含三个种子、共 **1,500 次混合存储操作**，定期重载并核对侧文件和原文件。

同一进程连续 **20 轮、340 组应用自检通过**，耗时约 **142.6 秒**。主要累计操作如下；请求数不等于实际解码数或真实用户复制次数。

| 操作 | 数量 |
| --- | ---: |
| RTF / HTML / RTFD / PNG 固定种子变异 | 5,120 |
| 采集取消、恢复、清理及重新展示循环 | 2,000 |
| 手动触发轮询 | 127,000 |
| 后台任务接收 / 满队列拒绝 | 8,000 / 400,000 |
| 缩略图突发请求 | 200,000 |
| 模拟快捷键替换尝试 | 40,000 |

所有测试使用合成内容、临时历史和命名剪贴板。快捷键压力项使用模拟后端，没有向其他应用发送按键，也没有读取个人历史或系统通用剪贴板。

随后仅补充测试断言，在相同生产实现上再跑 **3 轮、51 组自检通过**：真实后台调度器处理坏 RTFD 的纯文字回退与失败粘贴保护；旧界面测试退出后，窗口、视图和模型三个弱引用全部释放。最终安装包包含这些断言。

### 内存结果与限制

本次 20 轮的轮末物理内存从 **15.69 MiB** 到 **25.97 MiB**，测量期间峰值约 **176.92 MiB**。测试包含大图片解码，数值不代表正常使用占用；轮末数据也不代表峰值。原始数据见 [stress-0.1.8.json](../Benchmarks/stress-0.1.8.json)。

轮末内存存在增长，因此不能凭功能检查通过宣称“无泄漏”。框架缓存、分配器保留页、测试夹具与真实未释放对象需要分别判断。队列、缩略图缓存预算和弱引用释放断言只覆盖各自的对象边界，不是整个进程的内存上限。

补充三轮中，窗口、视图和模型释放断言通过，AppKit 窗口计数保持为 1，没有逐轮增加；轮末内存仍由 15.56 MiB 增至 16.06 MiB。额外尝试了 `leaks --atExit`：被测程序完成三轮，但诊断工具以 137 异常退出，未产生有效泄漏报告，诊断进程已确认退出。因此目前仍不能把增长归因于某一框架，也不能证明不存在泄漏；需要后续真实使用和有效内存剖析。
